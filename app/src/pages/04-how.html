04

AI 产品经理怎么做

案例：Oneport · 跨境电商运营 Agent 桌面端
前面看的是别人家的，现在看我们自己的：Oneport，子公司做的跨境电商 Agent 桌面端，我们对外卖的产品，基于浏览器操作，已上线。

明确来源

真实需求怎样算办好

落地一共五步，先看第一步：明确来源，也就是需求从哪来。从运营每天真在干的事开始收真实需求；每条需求不能只记一句愿望，要先定清楚怎样算办好。

在 Oneport 的目标（Goal）设计里，就把这件事做成了硬规定：每个目标必须同时写明「目标 + 验收条件」，缺了验收条件的候选目标会直接被丢弃。

设计上下文

规则核心提示 · PERSONA
数据OneBase 指标查询
记忆事实 / 经历 / 做法
Skills用时才取

第二步设计上下文，对应车上的挡风玻璃和行车记录仪，管它眼前看到什么、事后记下什么。屏幕上是三块内容，加旁边的 Skills：

第一块「规则」：放产品的核心提示和 PERSONA（用户自己写的角色与偏好指令文件），作为长期守则带在系统提示词里。

第二块「数据」：分清两处——经营指标都在云端 OneBase 数据仓，由模型按需调工具查；本地数据库约 60 张声明表，存的是会话、定时任务、目标、计划等本地运行状态。另外独立存着对话存档点（checkpoint），有了存档点就不再灌整份历史，超预算时先压缩。

第三块「记忆」：分事实、经历、做法三类。记忆功能默认是关的，开启后按需召回相关记忆。

把规则（spec）、记忆和旁边的 Skills 对比来看：规则是人定死的长期守则，每轮都带着；记忆是过去留下的事实、经历和偏好，开启后按需召回；Skills 是某类专项活的操作手册，平时只给模型看名字和简短描述，用时才取正文。

卖家精灵KeepaSif
tool_search → tool_get → tool_action

浏览器 15 个 · 数据 11 个 · 4 个按需取工具入口 · 卖家精灵在门后

第三步是明确能力里的工具设计，也就是给车装方向盘。纳入目录的模型可见工具共 55 项（44 项常驻，11 项需 OneBase 配置），其中浏览器 15 个、OneBase 数据 11 个，另外有 4 个按需取工具的入口。

云端远程工具和自配的 MCP 工具数量多，如果每轮都把全部工具说明放进上下文，会占掉大量上下文空间；只留 tool_list、tool_search、tool_get、tool_action 这 4 个入口，先列或搜、再取说明、最后调用，就能按需取工具。

Function calling 就在这里：模型说出要用哪个工具、参数是什么。

卖家精灵在 Oneport 里是云端远程工具，从这 4 个入口进去取，不是和 MCP 并列的另一样；另有一个浏览器插件形态，只做登录填充。

SP-API 的 284 个工具定义存在，但没有注册进来。

权限设计

影响别人 · 影响商品 → 先问运营

Oneport：澄清卡 · 工具白名单 · 没有系统级沙箱

第三步明确能力里的权限设计，就是定「哪些不能改」，也就是给车定交规、装护栏。对运营 Agent 来说，风险重点在「影响别人、影响商品」这类业务动作上，设计目标是碰到这些动作先问运营。

从设计层现状来看，Oneport 目前分三块：第一，开工前用工具白名单筛一轮可用工具（MCP 也只有允许和拒绝名单）；第二，没有操作系统级沙箱；第三，「先问人」是提示词约定加一张澄清卡，不是强制审批拦截，也没有「影响别人、影响商品」的自动识别。

也就是说，这条规矩今天主要靠提示词守着，把软约定补成硬护栏，正是产品经理要补的地方。

业务知识 Skills 化

口口相传 → 写下来

skill-creator · onebase-data-query

第四步业务知识 Skills 化，也就是固定成 SOP、给司机配驾驶手册（Skills），把口口相传的做法写下来。

屏幕上的两个名字代表两类技能：onebase-data-query 是查经营数据时优先加载的官方技能（另外飞书插件也自带了 27 个技能）；skill-creator 是用来创建个人技能的官方技能。

运营可以把日常摸索出的做法，通过 skill-creator 保存成个人的 SKILL.md，扫描入库后，后续会话就能检索加载。

设计任务闭环

触发定时任务
执行技能技能 + 工具
问人等待卡片
交付飞书机器人消息
留记录会话记录 · 执行日志
库存预警

这一页「设计任务闭环」还是第四步，是 Skills 写好以后让业务任务跑起来的那一圈。小圈 Harness 自带，大圈产品经理设计。02 章讲的「看 → 想 → 做」是干活时底座自转的小圈；屏幕上的「触发 → 执行技能 → 问人 → 交付 → 留记录」是产品经理要串起来的业务大圈。

画面上走的「库存预警」只是演示闭环怎么转，Oneport 里并没有这个专门模块。

看准三个实际边界：第一，交付是飞书或 Telegram 机器人发消息，不是直接生成飞书文档；第二，留记录是把会话记录和执行日志存进本地数据库，而记忆功能默认是关的，不能把记忆当留记录；第三，Oneport 跑在运营本机上，电脑睡眠或关机期间没有云端接班，错过的定时任务会记为「跳过」不补做，所以「24 小时盯库存」这种说法要慎用。

五步

  • ①明确来源
  • ②设计上下文
  • ③明确能力：工具设计 · 权限设计
  • ④业务知识 Skills 化
  • ⑤评测迭代

最后把这五步收个尾：第一步明确来源，从业务里收真实需求，定清怎样算办好；第二步设计上下文，配好挡风玻璃和行车记录仪；第三步明确能力，其中工具设计是方向盘，权限设计是交规和护栏。

第四步业务知识 Skills 化是给司机配驾驶手册；Loop 是 Harness 自带的小圈，产品经理要在这个小圈外面设计任务闭环，串起让业务任务从头跑到尾的业务大圈。

第五步是评测迭代：底层浏览器工具点得对不对，由大模型看截图判分；中间层单次任务跑得通不通，用自动检查脚本判分——这两层是研发测工具和底座。最顶上真实业务干得好不好，Oneport 目前没有业务任务集，要由产品经理定真实工作的考核指标。
